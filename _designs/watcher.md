Here is the complete, focused system design for **Watcher**, tailored specifically to its role as the high-throughput processing engine consuming tasks from Scavenger, handling 200,000 files per day, and writing structured data into OpenSearch.

---

## 1. Watcher’s Core Objective & Architecture Role

While Scavenger handles scanning, signature matching, and queue generation, Watcher serves as the distributed processing and normalization engine. Its primary responsibilities are:

* **Consuming** rule-specific hit queues asynchronously.
* **Fetching** the flagged raw files safely from Google Cloud Storage (GCS).
* **Parsing** file structures, metadata, and extracting indicators of compromise (IOCs).
* **Indexing** clean, structured JSON payloads in OpenSearch at scale.

## 2. Deep Dive Into Watcher’s Internal Components

### A. The Ingestion & Consumer Layer (`aio-pika`)
* **Role:** Listens to RabbitMQ queues generated by Scavenger without blocking threads.
* **Mechanism:** Uses asynchronous AMQP consumers configured with a strict `prefetch_count` (e.g., 10 to 20 messages per worker pod) to balance memory load and throughput.
* **Reliability:** Utilizes manual message acknowledgment (ACK on successful index, NACK/DLQ on structural failure or corruption) to guarantee zero message loss during peak traffic spikes.

### B. The Storage Fetcher Layer (Google Cloud Storage SDK)
* **Role:** Securely retrieves raw files based on object paths provided in the Scavenger queue message.
* **Optimization:** Instead of loading entire large payloads blindly into memory, it uses bounded chunked streaming or temporary secure container storage (`/tmp` inside ephemeral worker pods) to protect against memory leaks.

### C. The Core Parsing & Normalization Engine
* **Role:** Decodes headers, extracts deep metadata, parses file structures, and flags indicators of compromise (IOCs).
* **Implementation:** Built using a modular Python architecture where specialized parsers handle different file types (PE headers, archives, scripts, documents, etc.) before formatting everything into a unified JSON schema.

### D. The Bulk Ingestion Layer (`opensearch-py`)
* **Role:** Ships processed metadata efficiently to OpenSearch.
* **Optimization:** Implements asynchronous batching and bulk requests (e.g., flushing every 500 records or every 2 seconds) to prevent hammering the OpenSearch cluster with individual write operations.

## 3. Scalability & Resilience Strategy (200,000 Files/Day)

To sustain a continuous load of 200,000 files daily (~2.3 files per second on average, with higher peak bursts), Watcher is designed around horizontal scalability:

* **Kubernetes & Horizontal Pod Autoscaling (HPA / KEDA):**
  * Watcher worker pods are containerized via Docker and deployed on Kubernetes.
  * KEDA (Kubernetes Event-driven Autoscaling) continuously monitors RabbitMQ queue depth. If Scavenger dumps a massive batch of files, KEDA instantly scales Watcher worker replicas up to handle the volume and scales them back down when the queue drains.
* **Dead-Letter Queue (DLQ) Isolation:**
  * If a file is malformed, encrypted, or causes an unexpected parsing exception, Watcher catches the exception, logs the context, and routes the task payload to a DLQ. This prevents poison pills from blocking the main processing loop.
* **Stateless Worker Design:**
  * Worker pods carry zero local persistent state. Every file is fetched fresh from GCS, processed entirely in memory or ephemeral storage, and written directly to OpenSearch. This allows any worker pod to crash, restart, or scale without risking data integrity.
